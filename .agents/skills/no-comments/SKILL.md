# No comments

Comments in this repo are a last resort, not documentation. If a comment narrates or explains code you can read, rename, extract, or type better, it gets deleted — and when it was hiding a smell, the code changes instead.

Architecture prose belongs in `docs/`, `DESIGN.md`, `PRODUCT.md`, or the nearest `AGENTS.md`. Never in source.

See [PATTERNS.md](PATTERNS.md) for the full catalog with before/after examples from this repo.

## Delete on sight

- **Next-line narration** — `// Add "None" option at the beginning` above the line that adds it. Rename the variable or extract a function if intent is still unclear.
- **Section banners and step markers** inside a function — `// 1. Validate`, `// Merge into a single array`, `// First, build per-category …`. Extract a named function, or push the algorithm into a pure module.
- **Restated signatures** — `@param`/`@returns`/`@example` that repeat what the types and branch labels already say.
- **History and change-logs** — `// Mirrors the previous syncedDateRangeAtom write behavior`, `// new`, `// changed for X`. Git has it.
- **Workaround confessions** — `hack`, `temporary`, `for now`, `slightly wrong but`, `this is ugly but works`. The prose is a confession: fix the cause or open an issue and link it.
- **Commented-out corpses** — dead imports, dead props, dead extension entries. Version control is the archive.
- **Decoration** — banner rules, emoji, `AI-generated`/`Generated by` markers.

## Suppressions

`@ts-expect-error`, `@ts-ignore`, and `oxlint-disable` survive only when the rule itself is wrong. Research the type or the rule and fix the real problem. A `TODO: fix this` inside the suppression is not a fix.

## What survives

Keep a comment only when it names something outside our control, proven true today:

- Legal or license headers.
- Public API contracts that the type system genuinely cannot carry (a plugin's `afterCreate` ordering, an invariant callers must uphold).
- Behavior forced by a dependency, platform, vendor, or protocol we cannot reshape — cite the dependency.
- Issue or RFC links that explain a constraint code cannot express.
- `prettier-ignore` / `oxfmt-ignore`-style directives.
- A design-token label next to a bare literal (`// emerald` beside an rgba triple) when the literal cannot read as the token.

When unsure whether an exception applies, delete. A keep claim is verified before it is honored: read the dependency, the issue, or the call site. An unverifiable claim is deletion.

## Fix the cause, do not shrink the comment

Never rewrite a banned comment into a shorter version. Delete it, or make the code self-evident: rename, extract a named function, introduce a discriminated union or narrower type, add an early return, or add a test named after the behavior.

## Sweep

1. Take the scope from the caller — named files, or `git diff` against `main` plus the working tree. Never widen it.
2. Read nearby code before judging any comment. Classify each one: `KILL` (banned), `KEEP` (exception above, with the external thing named), or `MUST FIX` (the comment points at a real smell).
3. Delete kills. Do not polish them.
4. For `MUST FIX`, delete the comment and reshape the named symbol — but only inside the scope. An out-of-scope root cause gets reported open, never guarded with a fresh comment.
5. Report only what changed: files touched, deletion count, keeps with the constraint each cites, `MUST FIX` symbols with one line each, and anything left open.
6. Do not commit. AGENTS.md requires explicit approval for every git mutation.

## Writing new code

Write the code first with zero comments. Then add one only if it passes the exception list. If you catch yourself writing "this is non-obvious because …", that sentence is the specification for a rename, an extract, or a test — not a comment.
